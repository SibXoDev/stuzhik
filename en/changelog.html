Changelog ​

What changed in each version of Stuzhik. Search by words and narrow the list by kind and mark, say fixes only or experimental features only. The versions are listed under «On this page».

  • In the launcher the same list is in the «Versions» window → «What's new». It opens from the «Changelog» icon in Settings, the «Changelog» button in Documentation, a version card in the news panel and Ctrl+K → «Versions»
  • In a feed reader through RSS/Atom: subscribe in Feedly, Inoreader or your browser's built-in reader, and new versions come to you by themselves

How to read a version number: the middle number is a stage, a big release with new things, the last one is a patch to it with fixes. Releases are numbered this way from 0.1.0 on; before it the numbers ran in a row, and the patches of that time are marked «Patch».

Stuzhik 0.0.24

LatestPatch4219393November 18, 2026

New 42

  • BetaThe launcher for Linux: AppImage, .deb and .rpm. It needs x86_64 and glibc 2.38 or newer (Debian 13, Ubuntu 24.04, Fedora 39 or newer). It updates itself: the AppImage is replaced in place, the system installs updates of the .deb and the .rpm and asks for your password once
  • The «What to do» steps of the log analysis are checked against what the launcher knows about the build and run by a button. «Update the mod» checks for updates for the build's game and loader: when there is nothing newer, the step honestly says so and the next one becomes the recommended one; when there is, the button reads «Update to 6.0.11». «Disable» turns the mod off (an already disabled one offers «Enable again»), «Tell the author» builds the logs archive and opens the mod's issue tracker. Mods named in the cause's title and description are shown as the mod itself: icon, name, card on click. «Fix all problems» sits at the top of the tab next to «Check again»
  • «Overlaps» finds recipe clashes: two mods answering the same ingredients with different items (nine tin ingots make one mod's block or the other's), and the game takes only one recipe. It shows the crafting grid or the furnace with the items' real icons from the mods and every result with its mod. Recipe load conditions, the whole build's tags and the game's own recipes count. With KubeJS, CraftTweaker or a unifier mod in the build, it says so: the clash may already be solved there. If Polymorph exists for the build's game and loader version, the launcher offers it: with it the player picks the result of the same craft
  • The log analyzer finds a crash's main cause from the report's own structure: which mod failed, whose mixin did not apply, which mod lacks another mod or game version, out of memory, a broken config. It goes first, marked «Main cause», and a mod is named only when the report shows it. Checked on 93 real crashes from mods' issue trackers: the right cause in 90 (was 20), no wrong mod blamed (was 37). The F3+C debug report is no longer taken for a crash
  • The build's «Log analysis» tab got «Crash history»: how often and because of which mods the build crashed, what is already fixed and how each mod's crashes changed over the week. The launcher recorded it before, but had nowhere to show it
  • The console version is out for ARM too (aarch64: Raspberry Pi 4 and newer, ARM servers): an archive, a .deb and an .rpm next to the x86_64 files. The launcher downloads the server's Java for the machine's architecture
  • Console version: `stuzhik-cli update <build>` updates a build's modpack. First you see what changes: which mods are added, updated and removed, which of your own mods stay and which of your replacements of the pack's files are overwritten; it applies after a yes (or with `--yes`), with a backup first. `--to <version>` installs a given version. An update onto another game version is in the window app: it keeps a rollback point with the worlds
  • Console version: a server from a modpack. `stuzhik-cli create <name> --modpack <pack>` installs a modpack straight as a server (no client game resources) and turns its client-only mods off, naming them; mods that could not be identified are listed apart. A pack is a file (.mrpack, CurseForge .zip, .stzhk), `modrinth:<project>[@<version>]`, a modrinth.com address or `curseforge:<id>`
  • Console version: backups from the terminal. `stuzhik-cli backup <build>` makes one, `backups <build>` lists them, `restore <backup>` brings the build back, with `--worlds` the worlds too. It is the same backup code as in the window, the same backups are seen in both, and the window and the terminal do not get in each other's way even on one build at once
  • Console version: `stuzhik-cli console <build>` attaches to a server that `stuzhik-cli run` keeps in another terminal or as a systemd service: the last 200 output lines, then live output, and typed commands go to the server. Ctrl+C only detaches, the server keeps running. Only the same user can attach
  • ExperimentalA world moves to Horizon with one button: on the «Worlds» tab of a vanilla build of the same game version every world has «To Horizon», and a Horizon build has «To Minecraft» back. The world is copied, the original stays
  • A build added to Steam gets its own library cover, recent-games tile, page background and a logo with its name: from the build's cover, or without one the launcher's mark on the loader's colour. The «Build in Steam» window shows them beforehand. Pictures you set in Steam yourself are left alone
  • «Take from other versions» in «Build translation» finds Russian for CurseForge mods missing from Modrinth too: the mod is recognised by its file, and strings come from its newer files on CurseForge. The Twilight Forest for 1.21.1, for one, went from 1466 to 1916 Russian strings of 2055
  • The launcher can install ready translations of builds by the Stuzhik team by itself: it learns from our server which modpacks are translated and lays the translation after a build is installed or updated. The first translations will appear in the list later. «Settings → Mods → Build translations» can ask instead or be off; a translation you removed does not come back by itself, and your own translation file is never replaced. Russian of mods the team translated comes first, before other versions from Modrinth
  • Horizon starts with any account of the launcher, not only Microsoft: an offline or Ely.by account plays single-player, LAN and servers without the account check (the Horizon authors allowed it). The account is chosen the same way as for the usual game, by the same code
  • «Build translation» shows how many of the mods' strings are in Russian already, and «Take from other versions» fills in missing Russian from other versions of the same mods on Modrinth: only strings with the same English text are taken, only the language files are downloaded. An updated mod loses its taken strings until they are taken again
  • «Build translation» in a build's menu (More…): FTB Quests and Heracles quests, Patchouli books and KubeJS and OpenLoader texts the build carries itself, with bars showing how much of it is in Russian already. The strings go out to a file for a translator, the finished translation is loaded back and laid over the build; «Remove translation» brings the build's files back byte for byte. A string the build's author has rewritten since is left alone: it stays in English instead of getting a translation of the old text. The translation survives a modpack update (taken back before it and laid again after, a Russian file the author brought stays) and a game version change (the translation's resource pack is remade at launch)
  • Mods' built-in update checks are off by default: Mod Menu, Iris, Distant Horizons, Forge and NeoForge no longer announce new versions on every start, and Distant Horizons does not download an update by itself behind the launcher. The switch is in «Settings → Mods → Mod integrations», and a build can have its own choice in its settings
  • A build's shader or resource pack can be made shared with a button in its row: the file moves to the shared folder and is added to every build when the game starts. A shared shader's settings are shared too: tune it in one build, and after you quit the game it looks so in all of them. A build's own shader settings still win
  • Game settings for every build right in the launcher: «Settings → In game → For every build». Render distance, field of view, brightness, GUI scale, the FPS limit, volume, mouse sensitivity, auto-jump and more are set without starting the game. A category with «In every build» on is the same in every build, and what you change in the game comes back to the launcher; with it off, only new builds get the values
  • Shader presets: the «Preset» button of a shader pack in a build's «Shaders» tab shows the profiles the pack's author defined (for example Low, Medium, High in BSL and Complementary) and applies the chosen one to this build. The launcher changes only the pack's settings file, never the shaders, and your other settings of the pack stay
  • Graphics presets: in a build's «Game settings» its graphics can be saved under a name and applied to any other build. A preset holds the game's video settings, the chosen shader with its settings and the graphics settings of mods (Sodium, Iris, Embeddium, Distant Horizons and others); field of view, brightness, interface scale, controls and sound are left alone. A preset can be saved to a file and loaded from one, and the launcher tells you beforehand when a build lacks the shader or a mod it needs
  • ExperimentalPlaying with Steam friends: open your world to the network and your friends get «Join game» in their Steam friends list. Their launcher picks or installs the same build and connects them to you over the Steam network, no open ports needed. Turned on in «Settings → Steam»; it works through the Steam test app, so friends see you playing «Spacewar»
  • A build can be added to Steam as a non-Steam game: «Add to Steam» in the build's menu. It shows up in your Steam library, starts from Big Picture and on a Steam Deck straight into the game without the launcher window, and the launcher closes with the game, so Steam sees how long it ran. Steam has to restart to see the new game: the launcher restarts it only from a button that says so
  • A console version of the launcher for servers: stuzhik-cli. One file with no dependencies for any Linux (there are .deb and .rpm packages too, and a Podman or Docker image is built from it) makes, installs and runs Minecraft servers on any loader, runs as a systemd service, analyses logs and shows a terminal screen (stuzhik-cli tui) with the server console and a server.properties editor. The data is shared with the window app: a server made in the window runs from the terminal and the other way round
  • «Settings → Launch → Per-build settings»: see which builds hold their own memory, Java, arguments, game settings, backups or hooks instead of the global ones, and put them back for one build or for all with one button. Saving the build edit window no longer pins the memory to the build when the memory was not touched: such a build keeps following the global setting
  • Minecraft's tutorial hints are off by default: before a client starts, the launcher turns off the «Use WASD» and «Open your inventory» hints, the accessibility screen of a first start and the chat hint on a first server. They can be turned back on with the «Turn off Minecraft tutorial hints» switch in «Settings → In game → Language & hints»
  • Minecraft's narrator is off by default: it does not speak on a first start, and Ctrl+B no longer turns it on mid-game. The «Turn off the narrator» switch is in «Settings → In game → Language & hints», where it can be turned back on
  • A new build starts in your system's language when the game has that translation: Ukrainian, German, Chinese and over a hundred more, each game version with its own list. A language picked in the game itself is never changed. The «Game language from the system» switch is in «Settings → In game → Language & hints»
  • A new «Overlaps» view in «Dependencies»: the launcher reads the build's mod jars and shows which mods change the same game methods and where that is a real clash (two mods replace a whole method or redirect one call), which add the same materials (tin, steel, lead) and generate the same ore, and which embed one library at different versions. The report copies with one button, ready for a mod author
  • A friend's server in «Friends» shows how it is right now: latency, players online, version and the server's message, as the game's own server list does. The launcher asks the server when you open its room and on «Ask again»; when it doesn't answer, it says so
  • A build's «Files» tab got the same config editor as a co-op room and the «Builder»: every edit is kept in history, compared with the previous one and restored, search understands regular expressions, «Open in VS Code» saves its edits there too. With a co-op room open on the build, the edits reach its feed. The build's other files are in «All files», as before
  • When a new stable loader comes out for a build's game, the build's page shows «A new NeoForge is out: 21.1.78 → 21.1.88». «Move…» opens the same window as a version change: what happens to every mod, the rollback point and «Roll back». «Not now» hides it until the next version
  • The launcher's data can be moved to any disk: «Settings → Storage → Location», «Where the data is». Builds, worlds, Java, the database and logs move together: onto the same disk instantly (the folder is renamed on restart), onto another by copying with every file checked, after which the old folder is removed. Paths inside the database are rewritten by themselves, and the interface's settings stay. New installs on Windows keep their data next to the program instead of the roaming profile; where the data is already there, the launcher offers the move once. Portable mode: a portable.txt file next to the program, and everything, the interface's settings included, is kept in the data folder beside it. Uninstalling cleans a moved folder like the usual one: service data always, builds and worlds with the checkbox
  • ExperimentalHorizon mod catalog: the first tab of a Horizon build holds the mods, resource packs and shaders of Horizon's registry. Every file is checked before install against the registry's hash, the author's signature (when they sign) and what the file says about itself; anything the registry took down is not installed, and installed copies are turned off. Mods switch on and off with a toggle, a new version installs with a button. Native mods (Rust code running with your rights) are listed but not installed: Horizon's launcher builds them. Before Horizon mode opens the first time, the launcher warns that Horizon and its mods are third-party projects you run at your own risk, with links to the project
  • ExperimentalHorizon, Minecraft 26.3 rewritten in Rust: the title bar has a «Minecraft | Horizon» switch. In Horizon mode builds have no loaders and no Java mods: create a build, the launcher installs the game files, downloads Horizon and checks the project's signature before unpacking (anything unsigned or changed is not installed), prepares the resources and starts the game with your Microsoft account. Resource packs, shaders, data packs, backups, worlds and playtime work. Horizon updates with a button on the home screen. Horizon is unofficial and plays only with an account that owns Minecraft
  • Downloads pick the fastest servers by themselves: the launcher measures the Mojang, loader, Java and mirror servers at start and before installing a build, and downloads from the fast ones first. The ones that did not answer go last in line but stay on, and one file missing on a mirror no longer sends the whole mirror to the end. A new «Network» settings tab shows what answers from your network and what to do, for example that Forge will come through a mirror or that CurseForge is unreachable. The download limits and mirror switches moved there too
  • Discord status: while you play, your profile shows “Playing Stuzhik” with the Minecraft version, the loader and the time in game, and without a game “In the launcher” or “Building a modpack together”. In “Settings → Discord” you choose what exactly to show (version, loader, time, modpack name, your build's name, the “Get Stuzhik” and “Stuzhik website” buttons) and see how others will see it. On a public server your Discord friends get “Ask to join”: their launcher shows which build it will install (a catalog modpack, the game with its loader, or plain Minecraft for a server without mods) and starts the game connected to the server. Requests can be answered by hand or let in at once
  • Mod, modpack, resource pack and shader catalogs and a collection's mod list can be shown as tiles: the switch is next to sorting, one choice for every catalog, remembered. The “View modes” switches in the interface settings for instances, mods, modpacks and backups changed nothing - they are replaced by this same catalog choice
  • Changing a build's game version or loader now moves its mods and lets you roll everything back: before the change you see which mods update to a version for the new game (new dependencies they need are installed right away), which get disabled (no version) and what happens to the worlds; a rollback point with the whole build and its worlds is saved first, and until you press “Keep”, “Roll back” in the build brings mods, configs, worlds and the version back as they were
  • A mod for another game version or another loader is now visible before launch: the “Dependencies” tab has a new group “Not for this build” (for example, “AppleSkin is for Minecraft 1.21.11, this build is 1.21.1” or “Mod Menu is for Fabric, this build is NeoForge”) with a “Disable” button, and the pre-launch check window shows the same. Before, such a mod, dropped in by hand or left after a game version change, silently reached the launch and the game did not start
  • The «Modpack» tab can «Restore as in the pack»: it compares the mods folder with the installed pack version, brings back deleted pack mods and replaces changed files and mods moved to another version. Optionally it turns the pack's turned-off mods back on, removes your own mods and restores the pack's configs. The window shows everything before anything changes, and a backup is made first by default

Improvements 19

  • A «Download» page on the site: your system is guessed from the browser, each one has its button and terminal commands that copy in one click. The console version for x86_64 and ARM, a «Podman, Docker» tab that builds the image and checking a file against SHA256SUMS are there too. The button on the home page offers the package for your system right away
  • The launcher shows changes to a build's mods at once, wherever they happen: a mod disabled or updated in the log analysis, in another tab, by a modpack update or as a file in the folder - the mod list, the log analysis and the build's counters re-read by themselves, without reopening. The analyzer's step buttons answer every press: «Updating…», «Disabling…», then the result in the step itself and a notification, and an error shows right under the step. Saving the logs archive no longer hides the analysis behind the «Analyzing…» spinner and says where the file went, with «Show in folder»
  • The «Log analysis» tab got clearer: a crash's main cause is its own card in plain words, its mod is shown as installed in the build (version, whether it is disabled) with «update» and «disable» right there, and a click opens the mod's card. What to do comes as numbered steps in order, an automatic fix is a button inside its step, and the report line it was all read from opens under «How we know». Other findings are rows with a coloured severity icon and the mod with its icon and name instead of a technical id, its card a click away too. Rare actions (a single log file, the logs folder, saving the report, an archive for the mod's author) moved into the «⋯» menu
  • The log analyzer knows a mod by the build's own mod list when the crash report has none or a cut one, and reads «Mixins in Stacktrace»: when only the game's code is in the stack but mods' mixins changed it, those mods are named
  • «Overlaps» on Fabric and Quilt names the game's methods readably: `PalettedContainer.acquire` instead of `class_2841.method_12334`. The names come from Mojang's and Fabric's official tables, downloaded once; the jar's own name stays in the tooltip and next to it in the report, crash logs use it. Minecraft 26.1 and newer needs none: the game ships unobfuscated
  • ExperimentalWhen Horizon moves onto a new Minecraft version, builds on the old one no longer break: they play with the previous Horizon while it is on disk, and the build's page offers «Move onto …». The move is an ordinary version change: the whole build with its worlds is saved first, and «Roll back» stays
  • ExperimentalIn Horizon mode the catalog is laid out as for usual builds: mods from Horizon's registry in «Mods», resource packs and shaders in «Resources» and «Shaders», where the catalog can be Horizon's registry or Modrinth. «Modpacks», «Builder» and «Mod collections» are hidden in Horizon mode: they are about Java mods, which Horizon does not run
  • Settings drop their repeats: a block's caption that repeats the page title («Discord» under «Discord», «Connect settings» under «Connect») is hidden and its icon moved to the title. The line under «Settings» is gone too. Folder rows in «Storage» open with a click anywhere on the row, not on a small icon
  • Settings are reworked: sections are grouped in the left column, the big ones have sub-pages like the documentation, and a search over all settings sits on top (Ctrl+F), finding the captions inside sections too. Settings blocks became cards with the heading inside. The language picker now shows flags on Windows too, where letters stood in their place
  • Mod and modpack version lists: a game version filter next to channel and loaders (several loaders can be picked), and the list now has every version of a mod instead of the newest 30. A pack card opened from the catalog starts with the catalog's filter
  • In a build's dependency graph a mod can now be disabled or removed right from its panel (with the same “what breaks” window as in the mods list), and a missing dependency installed with the button next to it: only it and what it needs itself are installed. The graph does not lay itself out anew afterwards, nodes stay where they were
  • Backups no longer copy the whole build every time: identical files are kept once for all backups of a build. A backup of an unchanged build is instant and takes almost no space, after a mod update it adds only that mod, and a restore rewrites only the files that changed. The backups window shows how much they take on disk in total
  • The modpack install window no longer grows a wall of hundreds of “Asset …” and library cards: the pack's archive is one bar with its size and speed, and the game and mod files are one counter with the current file
  • The builds list on Home always shows what is really there: a build's status, settings, version, loader and cover, whoever changed them (the edit window, «Builds with their own settings», a version change, a rollback, a modpack update). The «Refresh» button on Home is no longer needed and is gone. A cover changes at once on the card, in the details and in the edit window, and no longer reloads at every game launch and stop. «Roll back» after a failed version change appears at once, and «Starting…» no longer flickers back to «Play» while the game starts
  • Lists no longer blink or rebuild whole: when something changes only the changed row is redrawn, and when nothing changed nothing is (one «not a problem» mark in «Dependencies» used to redraw every row with its icon). A removed mod leaves the list at the press, and the scroll stays where it was. While a mod installs from the catalog, the rest of the mods list stays usable. The mod details window no longer closes after an install: it shows «Installing», then «Installed» and marks the installed version, even when the install started from the card. A build's cover also shows in «Continue» on Home and in the build picker for co-op
  • A build's screenshots and worlds update by themselves: a new screenshot from the game, a new or removed world show at once in «Screenshots» and «Worlds», in the datapacks world picker and in the tab's number, with no «Refresh» button (it is gone). The launcher watches the folders only of the build you have open. Changes made by the console version stuzhik-cli on the same data (a backup from the terminal, a server run as a service) reach the window too, within a second
  • Categories in the catalogs of mods, modpacks, resource packs and shaders go in alphabetical order in the interface language, and loaders come in one order everywhere: no loader, Fabric, Forge, NeoForge, Quilt, and NeoForge is no longer spelled «Neoforge» anywhere. Categories used to follow their English names and looked shuffled in the Russian interface, and loaders stood in five different orders in different windows
  • «What's new» in the launcher and the changelog on the site show a version's changes by kind: new first, then improvements, fixes and changes, each group with its label and count. Entries used to come mixed, in the order they were added. Version cards in the news feed count the same way: «Changes» are no longer added to improvements, and «fixes» is no longer English in the Russian interface
  • «New versions available» in the «Modpack» tab counts only pack versions for the build's Minecraft version and loader. A version for another game, or NeoForge instead of Fabric, used to count as an update too. Such versions are now shown on a line of their own, and every version in the list shows its game and loader

Fixes 39

  • In the light theme the build's name in its header and the loader's name in badges («NeoForge», «Fabric») were white and nearly unreadable
  • The log analyzer's severity badges («Critical», «Error») now follow the interface language instead of always being English
  • The log analyzer writes in the interface language: in the English launcher problems, causes and fix advice are now in English (they were always Russian), and a few findings that existed only in English got Russian text. Hidden problems and solution feedback survive a language change. The console version writes the analysis in the system's language
  • The «did the fix help» feedback after an auto-fix is now saved where the launcher finds it again: it was recorded under the log line number and lost on the next analysis
  • The launcher window no longer hangs while the log analyzer reads and writes its marks («not a problem», disabled fix types, crash history)
  • SecurityA launcher update is accepted only when the file's signature was issued for exactly the announced version: a forged update list can no longer pass an old signed build off under a new number
  • A modpack update no longer turns on mods that were off: the new version of such a mod is installed turned off as well
  • A modpack update on a server no longer brings its client-only mods back: they are turned off again after the update
  • Modrinth modpacks install the way their author marks them: a file marked as unsupported on the server or the client is not installed there, and a server takes its own part of the pack (server-overrides) instead of the client's
  • Finding a server's client-only mods no longer remembers «unknown» for good: when Modrinth or CurseForge once did not answer, such mods were never checked again
  • Copying a world to another build no longer spoils a world of the same name there: the copy gets a new name («World (2)») instead of mixing into it. While either build runs the world is not copied, and an interrupted copy leaves no half world in the list
  • SecurityConnect no longer tells friends your public IP: only home-network and VPN addresses (Radmin, Tailscale, Hamachi) go out when you meet. A computer connected to the internet directly (PPPoE without a router, for one) used to hand its real address to friends
  • The install bar no longer sits at zero (Minecraft, modpacks, Horizon): it shows how many of the job's files are downloaded, and a single big file's bytes. Where the number is unknown, no empty bar is shown
  • Horizon shows the project's real logo, and its description names the right licence: LGPL-3.0, not MIT
  • Red and green buttons without a background (delete, unlink, accept) are coloured again: the button style overrode their colour and they were white
  • A chat line on a server can no longer replace the address the Discord status offers friends to join: the launcher reads it only from the game's own messages
  • Shared video settings now carry vertical sync too: the launcher did not recognise it in the game's settings before. A settings template can no longer be applied to a running build (the game would overwrite it on exit), and a template with a crafted name can no longer write a file outside the templates folder
  • The default memory and JVM arguments are now the ones the settings show even if they were never saved: such an install used to start the game with 512-2048 MB and no JVM arguments while the settings showed 2048-4096 MB
  • A build whose memory limit is below the global minimum no longer fails to start («Initial heap size set to a larger value than the maximum heap size»): the minimum never exceeds the limit
  • Installing a Minecraft version missing from the cached version list (the launcher started offline or the version is new) no longer fails with «Query returned no rows»: the list is refreshed, and an unknown version is named plainly
  • Log analysis finds the cause when Java dies before the game starts its log (for example, out of memory): the previous run's log was analysed instead
  • Modpack catalog: with a game version filter, «Install» takes the pack version for that game version instead of the newest one. The install window shows which version it will be beforehand and lets you pick another
  • ImportantA modpack update onto a version for another game version now saves the whole build with its worlds even with backups off and leaves «Roll back» on the build's page, as a manual version change does: rolling back brings the files, worlds, mods and the pack's version back. Before, worlds opened in the new game version could not go back
  • Deleting a build and other actions no longer fail with “database is locked” in the first seconds after start or while mods are being analysed: refreshing the Minecraft version list held the database for up to 11 seconds, and mod analysis held it while reading every jar file
  • The number of backups in the build's left panel changes right after a backup is created or deleted, not only when the build is opened again
  • A NeoForge, Fabric or Quilt build whose game version was changed no longer crashes a few seconds after launch: “Repair” now notices that the loader is left from the previous Minecraft version and installs the right one, and launching such a build says at once to press “Repair”
  • On Windows the launcher no longer stops following the game a few seconds after launch: a line a mod printed in Russian ended the reading of the game's output. After it the game console went silent, errors during play went unnoticed and joining a server was not seen. Installing Forge and NeoForge could hang until the timeout for the same reason
  • Cancelling the install of a Fabric or Quilt build takes effect at once: before, the launcher kept waiting up to two minutes for Fabric's servers, and the cancelled build could stay in the list with an install error instead of disappearing
  • A modpack install from the catalog can be cancelled from the first second: while the pack's archive was downloading, the “Cancel” button did nothing
  • The “Pixel trail” cursor effect no longer stutters on fast mouse moves. A jump across half the window built up to ten thousand points per frame and drew each one on the CPU; now the GPU draws the trail, with a few dozen points per jump at most
  • A mod published for several loaders no longer demands another loader's dependencies: LambDynamicLights on NeoForge asked for Fabric API, because Modrinth keeps one dependency list for all loaders and the Fabric manifest of a universal jar was read.
