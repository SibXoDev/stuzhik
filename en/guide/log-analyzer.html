Terms of Use

On this page

Log Analyzer ​

The game crashed: the analyzer tells you why it happened and what to do, with the buttons for it right in the steps.

It reads the crash report itself: the stack trace, the Mixins in Stacktrace section and the mods named there. It looks for the culprit by where the code failed, not by which mod the log mentions most. On real crashes from mods' issue trackers it found the right cause in 90 cases out of 93 and never blamed the wrong mod. The report is written in the launcher's interface language.

When it runs ​

  • By itself, after a crash. The analysis goes into «Crash History» and the analyzer opens. Even with the launcher's window closed, the crash still lands in the history
  • By hand. The «Analyze Logs» tab of the build page; «Check again» reads the logs once more
  • Without a window. stuzhik-cli analyze in the console version prints the same analysis

While you play ​

Errors show before a crash: «Live Monitoring» in the window's title bar follows the log while the game runs. A loading error (a KubeJS script, a mixin conflict) opens the analyzer at once.

The main cause ​

At the top is a card: what happened, in which mod and where that mod stands in the build (which version is installed, or that the build has no such mod). Under it, «What to do» lists steps in order, each with its button.

  1. Update. The analyzer checks by itself whether there is a newer version for this build and shows which one it will install. When there is nothing newer or the version is pinned, it says so instead of a button that would do nothing
  2. Disable. The mod is turned off in the build, «Turn back on» returns it. Already off: the step says so
  3. Tell the author. «Logs archive» packs this run's logs into a .zip, «Mod page» and «Issue tracker» lead to where to send it

A button shows at once what it is doing («Updating…», «Disabling…»). The result shows in the step itself: «updated to …, start the game», an error under the step too.

  • «How this was found»: the report lines it was decided from
  • «Details and solutions online»: the full description of the problem

Also found ​

Below the main cause is everything else the analyzer recognised in the log: not enough memory, a broken config, the wrong Java and more. These findings' steps are checked against the build too, and each row has the button of the first step the launcher does by itself:

  • Install. A missing mod is installed in the version the mod needing it accepts. There but disabled: the step offers «Turn on». Cannot stand next to another mod of the build: it says so
  • Update. The dependency is there in the wrong version: this one is updated, no second copy goes next to it
  • Delete the file. A mod's damaged settings file, exactly the one the loader named (a copy stays in .backup/config). A world's settings are looked for in that world's serverconfig folder
  • Fix it. Everything else the launcher can do by itself: «Increase the allocated memory», «Reinstall the mod» and the like

After such a step the finding says «Awaiting restart»: the next step is needed only if the crash comes back. «Details and solutions online» opens all of a finding's steps.

Fix everything at once

«Fix All Problems» shows what will be done for each finding, and «Apply Selected» does the ones you tick. Disabling a mod is not ticked in advance there: worlds holding its blocks are better not opened without it.

«Not a problem» hides a finding in this build, and later analyses no longer offer it. You can bring it back in «Manage dismissed».

Run logs ​

The tab next to «Log analysis» shows the files of the last run themselves: the game log, the detailed log, the crash report, a Java crash and the logs mods write into their own folders (KubeJS, CraftTweaker and others). Files older than this run are under «Older».

  • Colour by level. An error's stack trace is shown with its record
  • Filters. «Errors» and «Errors and warnings» keep only such records, with their traces
  • Search. Matches are marked, Enter and Shift+Enter go to the next and the previous one
  • «Next error» scrolls to the nearest error below
  • While the game runs, the open file is read again by itself, and «Follow the end» keeps its last lines on screen
  • A large file (over 16 MB) is shown from its end: that is where the last run is

The «More actions» menu (⋯) ​

  • «A single log file»: analyze one of the build's logs instead of the last run
  • «Open a log from disk…»: any log or crash report, not necessarily from Stuzhik
  • «Save the report» and «Open a saved report…»: the analysis to a file and back
  • «Log archive for a mod author»: latest.log, the end of debug.log, the latest crash reports and the Stuzhik analysis in one .zip
  • «Copy as Markdown»: the report to the clipboard, to paste into a chat or a GitHub issue
  • «Which fixes are allowed»: what the launcher may apply by itself

Crash History ​

The second tab next to «Log analysis»:

  • «Statistics»: how many crashes, how many this week, which mods are to blame most often and how many were fixed
  • «History»: each crash with its analysis, «Mark as fixed» marks a fixed one
  • «Trends»: whether crashes became more or less frequent

«Clear history» removes this build's records.

If nothing was found ​

«No problems detected» means the logs hold nothing the analyzer knows that gets in the game's way. Then make the «Log archive for a mod author» and send it to Telegram or to the mod's author.
